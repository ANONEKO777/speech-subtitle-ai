## 2. 三個候選在 117 段人工標註上的分數

C 各層：分歧 13/14、英被寫成日 20/20、碎片 12/12、日後接英 31/31、普通英 20/20、普通日 19/20。

- Y 的偵測是「整段一個語言」，一段裡有日文也有英文（沒有 300 ms 停頓）時只能選一個，輸出另一半就是丟掉。這是做法的限制，不是調參能解的。
- 候選 Y 在 `-l auto` 偵測為英文時，輸出是英文：日文講者的話被丟掉或被譯成英文。我沒有逐段聽，只看了文字。
- C 的兩處錯誤。**s0258**（5.4 s，操作者標「兩者」）：兩個引擎的文字都是只有日文，Qwen3 的字覆蓋整段，沒有尾端可補。我不知道英文在哪裡。**s0776**（4.7 s，標「日」）：Qwen3 與 Whisper 的文字都有「本日はありがとうございました。Thank you so much for your time today.」，所以 C 標成兩者。可能是標註錯，也可能是模型寫出了不存在的英文。這兩段我沒有能力判斷，需要操作者重聽（見 §6）。若 s0776 標註是「兩者」，C 是 116 / 117；若 s0258 標註是「日」，門檻 2 通過。這是假設，不是結果。
- **門檻選在同一份標註上看過。** 尾端門檻 1.5 s、碎片 1.8 s、單一拉丁字規則，都是看了這 120 段的結果與 P22 的資料後定的，沒有另外留一份沒看過的標註。所以 98.3% 偏樂觀，不能當成對新影片的預測。尾端門檻有一段平坦區：全片 777 段中，尾端 ≥ 1.0 s、1.2 s、1.5 s 的段數是 14、14、13（≥ 0.8 s 是 15，≥ 0.5 s 是 28），表示定在 1.0 到 1.5 s 之間差不多。
- 兩個引擎可能有共同的錯。C 只用 Qwen3 的文字，所以 C 的標記是「Qwen3 寫了什麼」，不是獨立判斷。標註是人耳，這是唯一獨立的部分。

## 4. 為什麼不是 Y，也不給 8 GB 與 CPU 降級

- Y 在 117 段上 89.7%，且有 11 段把日文講者那半丟掉。Y 在 3 個設定檔都能跑，但輸出沒有達到驗收，把它當成 8 GB 與 CPU 的備案就是靜默降級。所以 `ja+en` 在沒有 Qwen3 的機器上回錯誤，不降級。
- Qwen3 只在 `gpu-24gb` 設定檔下載（`backend/manager/profiles.py`）。CPU 沒有 CrispASR 的 CPU 版。VRAM：C 全片跑一次，`nvidia-smi` 峰值 9990 MiB，跑之前基準 3223 MiB（其他程式用的，包含在峰值裡），所以 Qwen3 自己約 6.8 GB。這是在一張 24 GB 的卡上量的，**沒有在 8 GB 的卡上跑過**，不能說它放得進 8 GB。Y 的峰值是 5545 MiB（基準 3227）。
- 訊息：8 GB 與 CPU 設定檔選 `ja+en`，會看到「日英混合影片需要 Qwen3-ASR，只有 24 GB 設定檔才會安裝」（缺檔時）或「Qwen3-ASR 沒有 CPU 版本」（CPU 模式時）。

## 5. 沒做的、沒量的

- 全片 54 分鐘端到端：結果見 PR 說明，不在這份決定文件裡。

- 尾端修補的失敗模式：尾端若是音樂或笑聲，會被辨識成文字（檢查：結果要先通過「不是日英以外的文字」）。全片有 12 段觸發，11 段是「兩者」，1 段（段 609）補上了 `Yeah.`。沒有量過其他的假陽性，因為只有 120 段有標註。

- 英文與日文的內容重複（口譯）兩邊都保留，不去重。操作者之後決定。
