# 規劃：把中文影片當作來源，翻譯成英文或日文

狀態：只有規劃，還沒有實作。2026-11-26 撰寫，內容來自對 `main` 的唯讀探勘。關於程式碼的說法都是從程式讀出來的，關於模型表現的說法都標明「還沒量過」。英文版是 `docs/ZH-SOURCE-PLAN.md`，兩份內容一致。

## 目標

使用者選一支有國語（普通話）語音的影片，App 產出兩樣東西：原本的中文字幕，以及翻成英文或日文的字幕。摘要、編輯器、匯出和燒錄字幕的功能，和英文、日文影片一樣。

主要使用者是想看中文影片的外國人，他們需要把影片翻成自己的語言（你在 2026-11-26 的回答）。中文字幕預設用繁體字，但不改用語：App 無法知道影片是台灣拍的還是中國拍的，所以只轉換字形，不把詞彙改成台灣用語。

中文不是翻譯的目標語言。把中文來源「翻成」繁體或簡體中文只是字形轉換，不是翻譯，所以不在這次範圍。

目前 App 完全不接受中文當來源。語言偵測只數日文和英文，中文語音會得到「無法判斷」。

## 探勘的發現

程式已經有現成的介面。一個來源語言就是 `backend/core/source_langs.py` 裡的一列，各輸出語言的路線放在 `backend/core/ja_routes.py` 和 `target_routes.py`，日文轉英文就是這樣出貨的。所以加一列 `zh`，再加一條中翻英和一條中翻日的路線，就能表達這兩組語言配對。

有兩個之前的假設要更正。第一，純日文用的是 whisper `large-v3-turbo` 加 `-l ja`，Qwen3-ASR 只用在日英混合的來源。第二，所有綁在「輸出是繁體中文」上的東西（`zh_tw.py`、台灣用語），都不會被中文來源碰到。

真正的三個卡點如下。

1. **檢查規則假設來源有空格或假名。**
   - 「必須有譯文文字」的檢查是數來源的單字數，所以中文永遠不會觸發。
   - 日文輸出檢查會接受任何漢字，只有在英文超過 5 個單字時才要求假名，所以「把中文原樣抄進日文行」的回覆會被放過。
   - 長度上限是以來源字元計算，沒有人量過每個中文字對應多少英文或日文。
   - 路線物件已經有 `needs_script`、`problem`、`density` 這幾個欄位可以修。
   - 判斷簡體字和日文漢字的差別，要用 JIS 字集而不是「只有簡體才有的字」清單，因為「国」「学」「会」兩邊都是合法的字。
2. **語音辨識的語言和字形都沒量過，而且「沒有空格」的處理只會透過這一列開啟。**
   - 不認得的語言代碼會被當成有空格的語言，whisper 的中文字會被黏成一個「單字」，就是 P22 對日文找到過的同一個毛病。
   - 專案裡沒有任何資料說明 whisper 或 Qwen3 寫出的是簡體還是繁體，也沒有說 CrispASR 是否接受 `-l zh`，更沒有說強制對齊器支援哪些語言。
3. **封閉的清單和預設輸出語言。**
   - 前端的 `SourceLang` 型別是封閉的，不認得的代碼會被當成 `en`。
   - `zh-TW` 這個預設輸出語言寫死在五個地方（`Settings`、`Request`、`JobBody`、`JobOptions`、命令列），所以中文影片不指定輸出語言會得到 422 錯誤。
   - `unspaced.py` 的斷行是照日文助詞和語尾設計的，所以兩個中文字之間的每個切點成本都一樣，字幕可能從詞的中間切開。

## 決定（這是我的建議，你想換就告訴我）

1. **引擎：先用 whisper `large-v3-turbo` 加 `-l zh`。** 不需要新模型、不需要新的登錄資料、不需要新授權或下載，每一種設定檔（包括只用 CPU 和 Mac）都能用，日文也是這樣做的。Qwen3-ASR 保留為量測後的備選，它會讓中文變成只有 24 GB 顯示卡才能用、沒有 CPU 路徑。選擇由下面的實驗 E1 決定，就像 P22 為日文做的，不靠假設。
2. **每個來源有自己的預設輸出語言。** 把五個地方的 `zh-TW` 常數換成一個函式 `default_target(來源)`：英文和日文來源維持 `zh-TW`（不變），中文來源預設 `en`。輸出語言選單只列出該來源允許的語言。這是讓其他部分變簡單的領域模型修改。
3. **新增 `zh` 來源列。** 允許的輸出語言是 `{en, ja}`，字幕切分規則 `CueRules(unspaced=True)`，數值由實驗 E3 決定（起點是沿用日文的數值）。它有自己的來源提示詞（中文口頭禪如「嗯」「呃」「那個」「就是」「然後」、被省略的主詞、人名），到英文和到日文的路線放在新的 `zh_routes.py`，仿照 `ja_routes.py`，並加上路線層級的 `needs_script`、`problem`、`density`。中翻日失敗時的退路，是留空或經由中翻英路線轉譯，由 Z1 依量測決定。另外要寫中文摘要提示詞（`summarize_map_zh_to.md`），因為現有摘要提示詞不是只有英文，就是寫死「日文」。
4. **中文字幕斷行。** 在 `unspaced._boundary` 加一個提示用的掛鉤，放入虛詞和連接詞（的、了、但是、因為、所以，以及繁體寫法），對日文不起作用，所以日文輸出維持逐位元相同，用現有測試和前後對照執行來證明。
5. **來源字形（你決定的）。** 中文字幕預設是繁體字，只轉字形。辨識之後、切分字幕和翻譯之前，引擎寫成簡體的文字會用字元層級的轉換器轉成繁體，已經是繁體的文字原樣通過。不套用台灣用語（`zh_tw.py` 的詞彙表不在這條路徑上）。另外有一個開關，讓想保留辨識原貌的人關掉轉換。我建議的轉換器是 OpenCC 的純 `s2t` 設定：它轉的是字，只用詞組表在「一個簡體字對應多個繁體字」時挑選，不改詞彙，這點和它的區域設定 `s2tw`、`s2twp` 不同。這段描述來自我自己的認知，要在 E2 查證，授權也要查（我所知 OpenCC 是 Apache-2.0，同樣未查證），並要找純 Python 的移植版，這樣在 Windows 和 Mac 上都不需要原生編譯。已知的出錯來源是一對多的字（例如「发」「后」「干」「里」），所以 E2 要在真實文字上量轉換器的錯誤。
6. **偵測是方便功能，不是門檻。** 手動選中文，專案就能正常運作。自動辨識中文放到後面的波次（Z3）：`LANGUAGES` 要超出混合來源的兩個成員，`Sample.clear` 和 `decide` 要改，前端的 `Detection` 型別要通用化，中文和日文在短片段上的混淆要先量測。
7. **不在範圍：** 粵語和其他方言、中英夾雜的演講（混合路徑目前會拒絕簡體字）、中文當輸出語言、說話者標記。

## 波次（每一波一個 PR 加獨立驗證者，Z0 不改產品程式）

- **Z0，實驗。** 用 GPU，一次只跑一個模型。
  - E1：whisper turbo（`-l zh`）和 Qwen3-ASR（有無強制對齊器）的國語字錯率、即時倍率和顯示卡記憶體用量，CrispASR 是否接受 `-l zh`，以及各自寫出的字形和標點。
  - E2：whisper 和 Qwen3-ASR 對台灣國語和大陸普通話寫出什麼字形，初始提示詞能否讓 whisper 改寫繁體，以及簡轉繁轉換器在真實文字上的錯誤率（先選好轉換器並查授權）。
  - E3：國語語速（每秒幾個字）、字幕大小設定，以及每個中文字對應的英文和日文輸出長度，用真實翻譯量。
  - E4：whisper 對 5 秒片段的語言辨識，中文對日文對韓文。
  - 產出是一份有數字的決策文件，像 `docs/P22-japanese-asr-decision.md`。
- **Z1，後端。** `default_target(來源)`、中文字幕轉繁體（有開關，預設開啟）、`zh` 來源列、`zh_routes.py`、提示詞、檢查規則、斷行掛鉤、摘要提示詞、命令列（`--source-lang zh --lang en`）、測試和突變測試，以及一個結構檢查：每個來源列對它允許的每個輸出語言都有一條路線。
- **Z2，前端。** `SourceLang` 加入 `zh`，標籤、標記和說明（「中文：字幕為英文或日文」），輸出語言選單依來源過濾，匯出檔名（`<影片>.zh.srt`），媒體庫標籤。這一波排在多國語系的 W2 之後，字串才能直接進字串表，不用再進舊的對照表。
- **Z3，偵測（可選）。** 如決定 6。
- **Z4，品質檢查。** 在真正的視窗用真實影片端到端跑一遍，由你閱讀中翻英和中翻日的輸出，用詞彙表修正反覆出現的錯誤（像 P25 和 P30 做的），檢查燒錄字幕中的中文來源行（Windows 和 macOS 都要用中文字型），更新 README、SPEC 和功能文件（「只辨識英文和日文」這句話不再成立）。

## 測試音檔和品質

專案裡沒有中文音檔（只有一支英文測試音檔和示範影片）。量測用的資料集，我提議用授權開放的公開朗讀語音集：Mozilla Common Voice（zh-TW，CC0）、FLEURS（國語，CC BY 4.0）、AISHELL-1（Apache-2.0）。這些授權名稱是我憑印象寫的，沒有查證，使用前先確認，你已經同意下載。長片的行為（字幕切分、摘要、翻譯）我需要你提供的台灣中文演講，因為我挑的東西必須能合法放在專案旁邊，而你的私人影片不需要。中文語音辨識除了字錯率之外沒有標準答案，所以翻譯品質靠結構檢查（P25 測試的模式）加上你閱讀樣本來判斷。

## 風險

- 台灣人說的話，whisper 可能寫成簡體字，也可能少寫標點（還沒量過）。
- Qwen3-8B 可能把產品名稱變成中文音譯，而英文和日文輸出應該用拉丁字母或片假名寫。詞彙表和詞彙對照表是現有的處理方法。
- 簡轉繁會因為一對多的字出錯，所以由 E2 量錯誤率，並且保留關閉轉換的開關。
- 中翻日用的這組模型從沒評估過。字數和字形檢查是安全網，退路是一個要決定的設計，不是猜測。
- 多國語系的工作也會修改 `app/src/api/sourceLang.ts`，Z2 等它做完，避免衝突。多國語系規劃裡寫的「日文或英文輸入」要在中文上線時更新。因為使用者是外國人，App 自己的介面語言也很重要，多國語系的預設值會在 W5 從 `zh-TW` 改成 `auto`。

你的演講檔案，以及外國人之後還需要英文和日文以外的哪些輸出語言。路線表是依輸出語言分開的，所以多一個輸出語言只是多一條路線，不是重新設計。Z0 現在就可以用公開資料集開始，你的演講檔案到了再加進去。
